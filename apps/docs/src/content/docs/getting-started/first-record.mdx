import { Aside, CardGrid, LinkButton, LinkCard, Steps, Tabs, TabItem } from '@astrojs/starlight/components';

<Aside type="tip" title="5 minutes from YAML to a rendered page">
  Write a single record file (`data/records/my-project.yml`), save it, and watch the dev server render it as a project detail page at `/projects/<slug>/`. Three actions: create the file, validate, push.
</Aside>

<Aside type="note" title="Prerequisites">
  - Node `>=22.12.0`
  - A Node package manager — pnpm, npm or bun (the tabs below cover all three)
  - A scaffolded Grove space with `pnpm dev` running locally — see [Scaffold a space](/getting-started/scaffold/).
</Aside>

<Steps>

1. ### Create the record

   Create `data/records/my-project.yml`. The filename (minus `.yml`) is the canonical slug and appears in URLs.

   ```yaml title="data/records/my-project.yml"
   kind: project
   name: My Project
   slug: my-project
   description: A short description of what the project does and who it is for.
   category: developer-tools
   tags: [open-source, typescript]
   repoUrl: https://github.com/example/project
   links:
     website: https://example.com
     github: https://github.com/example/project
   bestFor: [Team workflow, Quick start]
   whyListed: [Active maintenance, Clean API]
   caveats: []
   visibility: keep
   ```

   <Aside type="tip" title="Prefer Markdown?">
     The same record can be one Markdown file, `content/records/my-project.md`: the fields go in the frontmatter (you can leave `slug` out — the filename is the slug) and the notes shown on the detail page go underneath.

     ```markdown title="content/records/my-project.md"
     ---
     name: My Project
     description: A short description of what the project does and who it is for.
     category: developer-tools
     repoUrl: https://github.com/example/project
     addedAt: 2026-09-27
     submittedBy: your-github-login
     ---

     ## Why it's listed

     The notes shown on the detail page.
     ```

     `addedAt` orders "Recently added"; `submittedBy` shows "Submitted by @login" on the page. Both work in YAML too.
   </Aside>

   <Aside type="note" title="What you should see">
     Save the file. The dev server picks it up immediately and the project appears in your local directory at `http://localhost:4321/projects/my-project/`.
   </Aside>

2. ### Validate the record

   Run the full pipeline at any time:

   <Tabs syncKey="pkg">
     <TabItem label="pnpm" icon="seti:notebook">
       ```bash
       pnpm exec grove check
       ```
     </TabItem>
     <TabItem label="npm" icon="seti:notebook">
       ```bash
       npx grove check
       ```
     </TabItem>
     <TabItem label="bun" icon="seti:notebook">
       ```bash
       bunx grove check
       ```
     </TabItem>
   </Tabs>

   <Aside type="note" title="What you should see">
     You should see `[grove] 1 records prepared; sitemap and llms files updated.` and an `astro check` summary. If a field is wrong, the error points to the file and field name. Fix and re-run.

     `grove check` is the only command you need for day-to-day validation — it bundles `validate`, generation, sitemap, llms, robots, og-image, and `astro check` into a single invocation.

     `grove init` writes no CI workflow. To run `grove check` on every pull request, copy one from the Grove repo — see [Workflows](/outputs/workflows/).
   </Aside>

3. ### Publish

   When you're happy with the record:

   ```bash
   git add data/records/my-project.yml
   git commit -m "Add My Project"
   git push
   ```

   <Aside type="note" title="What you should see">
     Open a pull request. With a CI workflow in place it runs `grove check` and the build; a maintainer reviews and merges, and your host rebuilds the site (see [Deployment](/deployment/overview/)). If `integrations.github` is enabled and you copied `sync-github.yml`, it runs `grove sync github` weekly and opens its own pull request that updates only `data/cache/github/` — see [Sync GitHub metadata](/automation/sync-github/).
   </Aside>

</Steps>

## Required fields

For the `project-directory` blueprint (`kind: project`):

| Field          | Required | What it is |
| -------------- | -------- | ---------- |
| `kind`         | auto     | Grove fills in `project` for you if you omit it — it always matches the `project-directory` blueprint. Real records write it anyway, for clarity. |
| `name`         | yes      | Human-readable name. Shown in cards and headings. |
| `slug`         | YAML: yes · Markdown: no | In a YAML record it must be a non-empty string, but the build always uses the filename as the canonical slug — a mismatch only produces a warning, not a failure. Keep them the same to avoid confusing the next contributor. |
| `description`  | optional | One-sentence summary. Shown in lists and search snippets. Defaults to an empty string if omitted — write one anyway. |
| `category`     | optional | One of your taxonomy categories. Defaults to `uncategorized`. |
| `tags`         | optional | Free-form labels for filtering. |
| `repoUrl`      | optional | Canonical GitHub URL. Powers `grove sync github`. |
| `links`        | optional | URLs to website, GitHub, docs, source. |
| `stack` / `stacks` | optional | Stack chips on the card. |
| `platforms`    | optional | Platform filter chips. |
| `bestFor` / `whyListed` / `caveats` | optional | Curator notes — surfaced on the detail page. |
| `visibility`   | optional | `highlight` / `keep` / `needs_review` / `hide` / `remove` / `historical`. Defaults to `keep`. |
| `addedAt`      | optional | ISO date the record joined the directory. Orders "Recently added". |
| `submittedBy`  | optional | GitHub login of the submitter. Shown as "Submitted by @login" and on the contributors page. |

The full schema is in [Project record reference](/reference/record-schema/).
